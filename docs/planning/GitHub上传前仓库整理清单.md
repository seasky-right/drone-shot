# GitHub 上传前仓库整理清单

更新日期：2026-09-20。状态：待执行的整理要求；本轮只完成文档和旧综述存档。

## 1. 目标与顺序

建立轻量、可安装、可测试、可交接的源码仓库。本机运行资源与历史回归基线完整保留，通过显式资源说明连接到开发仓库。

建议两阶段整理：

1. **初次上传前**：保留现有代码路径，补文档、忽略规则、安装与测试入口；只提交明确选中的源文件和小型资料。
2. **后续独立 PR**：在新 Backend 可运行且迁移验证通过后，再整理 legacy、第三方依赖和资源路径。不得一边修改功能一边大规模搬移旧材料。

上传一个“基础代码 + 待办明确”的仓库是允许的，不必等真实 Backend、搜索任务或 Benchmark 全部完成。上传准备与三 track 独立开发的协议冻结是两个不同关卡。

## 5. 根级文件的最低内容

| 文件 | 必须包含 |
| --- | --- |
| README.md | 项目定位、当前能做/未完成、规划入口、安装、无仿真测试、真实仿真入口、已知限制 |
| CONTRIBUTING.md | 小任务分支和 PR 流程、目录责任、接口变更确认、验收证据与交接格式 |
| AGENTS.md | 文档依据、冻结基线边界、允许修改的模块、测试分层、禁止用假结果代替真实验收 |
| pyproject.toml 与锁定文件 | 支持版本、显式包发现范围、核心/开发/Backend 可选依赖；避免把全部课程文件打包 |
| 配置示例 | 资源根路径、连接参数、载具/相机选择、任务参数；本机覆盖文件不提交 |
| .gitignore | 下列排除类别，并验证真正生效 |
| .gitattributes | 文本及二进制分类；根据脚本需要约定换行，避免无意改变冻结文件字节 |
| PR 模板 | 需求、协议影响、验证结果、遗留事项、交接下一步 |
| CODEOWNERS | 实际 GitHub 账号与目录责任；账号未确定前不得使用虚构用户名 |
| CI 工作流 | 干净安装、明确测试范围、无仿真契约/Mock/fixture 测试 |

项目代码的许可证需由有权决定的人确定；第三方组件保留原许可证和来源，不自动套用项目许可证。

## 6. 忽略与资源获取规则

忽略规则应覆盖以下类别，但不能仅凭扩展名误排除所有有用 fixture：

- `.driver-cache/`、`.doc-review/`。
- `__pycache__/`、`*.pyc`、测试/工具缓存、`*.egg-info/`、build/dist。
- `.vs/`、`.idea/`、`*.vcxproj.user` 等机器专属工程状态。
- UE 场景包、解压运行目录、Saved 日志/崩溃/机器状态、转储文件。
- 环境目录、私有环境文件、机器专属配置；公共 example 配置明确保留。
- runs/、experiments/、生成图像/数据及临时报告；小型 fixtures 单独纳入。

普通 Git 的提交列表应按白名单审阅，而不是在写好 .gitignore 后直接相信全部文件都可上传。

每个外置资源的 manifest 至少写清：资源 ID、版本、来源或团队获取方式、大小、SHA-256、解压布局、所需相对路径、许可证/访问条件以及对应运行说明。初期允许人工放置资源后校验，不必先开发下载器。

## 7. 冻结基线与路径迁移的特殊要求

当前 `freeze_baseline.py` 以根目录下原材料目录及 `airsim-settings/drone.json` 为源，manifest 含 1,389 个条目，其中也包含部分未来不应进源码仓库的运行/IDE 文件。

- 保留原 manifest 作为历史基线证据，不能直接执行 --write 将清理后的目录当成同一个未变基线。
- 初次上传可以保留历史 manifest，但 README 必须说明：仅源码 clone 缺少外部资源时，现有完整基线校验不适用。
- 后续新增“版本控制源码校验”和“已安装外置资源校验”两条路径，并明确与旧 manifest 的对应关系。
- 普通 CI 不运行需要完整旧材料的基线校验；本机资源齐备时单独执行。
- 要移动旧目录时，先验证源与目标都在预期工作区内，保全原件，再统一修改路径解析、配置说明和测试；迁移通过后才切换入口。
- 修改换行规则或清理文件也可能改变 checksum。冻结文件初次纳入 Git 后应检查干净 checkout 的字节一致性，再决定针对它们的属性规则。

## 8. 测试与接力规则

无仿真测试从当前可用命令开始：

```text
python -B -m unittest discover -s simulator_contract/tests -v
```

后续按明确目录加入平台契约、Mock、Task/Evaluator fixtures。不要在全目录盲目发现课程代码中的仿真示例测试。

真实仿真 smoke test 作为本机显式动作，记录系统/场景/代码版本、命令和结果；不放进每个 PR 的通用检查。旧基线校验也属于独立资源检查。

建议采用单仓库、集成主分支和按小任务创建的短期分支。每个 PR 可独立审阅、验证与撤销；协议变更单独提交，由 A 维护并记录受影响 B/C 的确认。

如仓库权限和套餐支持，可配置主分支要求 PR、测试通过和审查。CODEOWNERS 用于路由审查；同一路径写多个 owner 默认不要求所有人全部批准，协议三方确认需另外留记录。[GitHub CODEOWNERS 说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)

交接最少字段：当前提交、任务编号、依赖协议版本、完成内容、实际测试、遗留问题、下一条具体动作。不以聊天历史作为唯一交接材料。

## 9. 上传前验收清单

### 文件与范围

- [ ] 根级入口能指向当前路线、近期计划和实际状态。
- [ ] 旧综述已归档，PRD 的现实偏差有说明；本轮已完成，上传时复核路径。
- [ ] 选定的源码及第三方补丁完整，许可证和来源没有丢失。
- [ ] 驱动、仿真大包、缓存、crash dump 和机器配置未进入待提交列表。
- [ ] 已审查绝对路径、凭据/令牌、个人会话和不宜公开的材料。
- [ ] 仓库可见性、拥有者和协作者已确定；外置资源有实际可用的获取途径。

### 可运行与可交接

- [ ] 干净环境可安装并通过当前无仿真测试；没有隐式依赖共享 Python 包。
- [ ] 普通安装和 CI 不要求存在场景大包或原始课程完整目录。
- [ ] 外部资源缺失有明确说明/错误，不静默回退到开发者本机路径。
- [ ] 真实测试说明可执行，历史飞行证据与当前代码验收分开。
- [ ] PR 模板和责任规则可用，未冻结事项链接到冻结清单。

### Git 初次提交

- [ ] 初始化前确认仓库根目录，避免把上层项目或本机材料整体纳入。
- [ ] 在首次暂存前设置忽略及换行规则；逐项审阅暂存文件。
- [ ] 检查暂存文件大小与敏感内容，而不只检查当前目录总大小。
- [ ] 通过独立 checkout/复制的干净目录验证文档链接、安装、测试和保留基线的字节要求。
- [ ] 首次提交描述准确表述“已有适配层与规划基线”，不宣称完整平台已完成。
- [ ] 推送到约定远程后，检查展示内容和 CI 结果，再开始按 Issue/PR 接力。

本清单要求先完成可审阅的本地整理；远程地址、可见性与第三方资源分发条件未确定时，不自行假定公开发布。
