# 前置条件冻结清单

更新日期：2026-09-20。与 [近期开发执行计划](近期开发执行计划.md) 配套。

## 1. 冻结的含义与分级

除明确标注的“已有底层约定”外，本文件原为待冻结清单。2026-09-21，F01—F06/F09 的最小默认基线已实现并通过本地验收；这不等同跨 track 或真人确认，详见 [P0-P1 本地验收报告](../validation/P0-P1验收报告.md)。

冻结至少需要：版本化定义、合法和非法样例、针对边界的测试、负责人及受影响 track 的确认记录。涉及真实仿真的事项还需要真实验收证据。一次 PR 或提交应把这些材料关联起来。

分三批处理，避免为了远期需求过度设计：

- **G0：分线开发前**。公共类型、生命周期、数据/坐标、动作语义、错误与环境。
- **G1：首次真实合流前**。场景实际能力、ReachPoint 规则、安全收尾及真实验收参数。
- **G2：对应扩展前**。SearchTarget 的检测/真值链路、批量实验的 seed 和统计规则。

仓库轻量初次上传不要求 G1/G2 全部完成。未冻结事项必须公开记录，不能作为其他 track 默认成立的依赖。

## 2. 已有底层约定

来源：[simulator_contract/README.md](../../simulator_contract/README.md)、[contracts.py](../../simulator_contract/contracts.py)。这些约定已在代码中表达；平台层如何采用仍须 F01/F03 明确。

| 事项 | 已有定义 |
| --- | --- |
| 协议版本 | `drone.simulator.contract/v1` |
| 距离、速度、时长 | 米、米/秒、秒 |
| 世界/机体坐标 | NED / FRD |
| 姿态 | 相对 NED 的单位四元数，顺序 w、x、y、z |
| 时间 | 可缺省的 simulator_time_ns、必有的 wall_time_ns |
| 资源标识 | 不透明 vehicle_id / sensor_id；支持某类操作不等于已发现某个传感器 |
| 传感器数据 | 元数据与二进制 payload 分离；不能把大图像直接塞进 JSON |
| 错误 | ErrorCode、ContractError；读取失败使用结构化异常，命令使用结果封装 |

旧基线 checksum 已验证一致，但不保证场景仍能运行；传感器类型支持也不保证实际资源可用。

## 4. G0 的具体决策

### F01：平台协议与底层协议的关系

建议保留 `simulator_contract/` 作为底层控制/传感器边界，新增 `contracts/` 表达平台运行所需类型。B 的 AirSimBackend 聚合底层能力；Core、Task、Agent 不访问 AirSim RPC 或旧材料内部实现。

冻结内容：

- 两层 Observation 的含义和映射。现有传感器 Observation 保留；平台类型采用明确名称或导入别名，禁止无区分混用。
- 平台独立 schema 版本；不能把底层 v1 当作平台 v0.1 已冻结的证明。
- A 维护跨 track 平台契约；B 维护仿真协议映射；影响消费者的变更需 B/C 确认。
- 新增可选字段、未知字段处理、破坏性变更和版本兼容规则。

### F02：最小公共数据和接口

至少逐项确定下列内容，不要求一次加入远期 GIS/RL/多机字段：

| 对象 | 需要明确的内容 |
| --- | --- |
| TaskSpec | schema、任务标识/类型、任务参数、初态需求、限制、seed；任务需求与机器连接配置分离 |
| BackendConfig | Backend 类型、连接参数、资源路径、车辆/相机选择与兼容选项；无本机路径的公共示例 |
| Observation | step/sequence、车辆状态、传感器引用、采样时间、缺失原因；不把评测真值默认暴露给 Agent |
| Action | action_id、类型、参数、坐标/单位、时长或 deadline、目标载具；未知动作如何拒绝 |
| StepResult / EpisodeEvent | 是否引入统一一步结果；动作结果、动作后观察、事件来源和顺序；执行错误与任务事件分开 |
| EpisodeResult | episode_id、任务/运行版本、终止原因、成功与否、收尾结果、指标、记录位置 |
| Agent/Backend/Task/Evaluator | reset、act/observe/execute、update、result、close 的实际签名和返回类型；connect 是否由 reset 内部承担 |

建议传给 Task/Evaluator 的过程数据显式包含 observation_before、action、execution_result、observation_after。名称可以调整，但必须避免只评估动作前状态而漏掉最后动作结果。

同时确定数值是否合法、空值含义、JSON/YAML 到类型的解析和校验失败格式。fixtures 与 Mock 必须使用同一实现定义。

### F03：坐标和数据时间

- 建议平台继承已有 NED/FRD 和 SI 单位，避免再引入无必要的坐标转换。
- 补充世界原点、home 定义；altitude 是相对 home、地面还是其他基准，不能只写“高度”。
- move_to 使用世界坐标；速度动作必须区分世界 NED 与机体 FRD，yaw 的单位与参考方向明确。
- 仿真时间与墙钟时间不能混减；建议超时和耗时预算使用单调时钟，墙钟只用于外部关联，仿真时间用于状态采样。
- 记录图像/位姿各自采样时刻与序号，不把先后 RPC 调用伪装成严格同步。
- 明确 RGB 编码/通道、深度单位与编码、图像帧坐标、无效像素和缺失传感器表达。

### F04：动作执行、失败和重试

建议 v0.1 采用有明确时限的同步 execute；在契约中说明完成标准，暂不预设复杂异步调度。

- 明确 accepted、completed、success 的区别；失败和超时后状态未知如何表达。
- 底层 `_command()` 当前忽略 RPC 返回值并直接报告完成，需要在 B 工作包中核实并修正语义，不把当前返回当成到达证据。
- 定义起飞/降落/移动/悬停/采集/返航的参数、前置条件、完成判据、最大时限和能力要求。
- 同一动作重试是否可能重复执行；超时后应先核实状态，不能对所有飞行动作盲目重试。
- 区分参数错误、能力不支持、连接失败、执行失败、超时及取消；底层异常在 B 边界转换。
- 统一事件中的 command/action 标识，保留原始诊断信息但不泄漏底层对象到平台接口。

### F05：生命周期、终止与清理

建议职责：Runner 控制循环和全局预算，Task 判断任务进度与目标达成，Evaluator 计算表现，Backend 执行控制与实际安全收尾。

必须确定：

1. 初始化先后顺序，以及 reset 完成后的可预期状态。
2. 一次循环的动作前后观测、事件、Task/Evaluator 更新和记录顺序。
3. success、任务失败、超时、取消、Backend/Agent/Task/Evaluator 异常的互斥终止原因及优先级。
4. Task 结束结论如何传入 EpisodeResult；Evaluator 不能另写一个与 Task 冲突的成功结论。
5. 最后一步、初始化失败和异常路径是否仍保存结果。
6. close 只断连接还是包含飞行收尾；建议显式区分收尾与释放资源，避免默认 close 即等于安全降落。
7. 收尾失败作为独立结果记录，保留原始终止原因；谁拥有进程就由谁按约定清理进程。

### F06：记录格式与复查能力

至少冻结 episode_id、step_id、action_id 的关联，配置快照、schema/代码/场景版本、实际车辆与传感器配置、动作前后状态、错误和收尾记录。

建议目录为 `runs/<episode_id>/`，包括任务配置、`result.json`、`trajectory.jsonl`、`events.jsonl`、图像文件及引用。路径应相对 episode 目录，可携带到其他机器。明确文件写入失败时如何标记不完整 episode。

依靠一个小型完整 fixture 证明：读者可找到每个动作的前后状态、最终结果及对应图像；缺失数据有原因，不使用零值冒充有效测量。

### F09：环境与协作

- 建议以当前验证过的 Python 3.13 为首个支持版本；精确补丁版本、平台范围和依赖版本在安装验证后锁定。
- Core/Mock 安装不应强制包含 UE、AirSim 场景或图形依赖；真实 Backend 依赖单独声明。
- 不要求接手者使用同一个共享 Anaconda；以干净环境复现作为验收。
- 初期保持已有源码目录，新增模块采用单一导入约定；是否后续迁移 src 布局另做独立变更。
- 确定 A/B/C 的实际负责人、审查人、集成责任人和接口变更确认方式；未提供账号前不填虚构 CODEOWNERS。

## 5. G1：真实合流前再冻结

### F07：实际能力矩阵

B 提供实测表：reset、takeoff、move_to、hover、capture RGB、capture Depth、return_home、land、碰撞读取、目标真值、场景重置。每项标注支持、受限支持、未验证或不支持，并附证据。

同时固定场景包校验值、客户端/适配器版本、启动步骤、实际载具与相机标识、配置有效范围、兼容性降落标准和资源清理职责。`drone.json` 不作为已被旧场景可靠读取的证据。

已有隐藏窗口验收不等于无渲染 headless；近期真实测试可以依赖本机 Windows 图形环境，不要求通用 CI 运行 UE。

### F08：ReachPoint 任务与验收数值

C 定义到达容差、停留条件、完成时间和路径长度公式；B 确认初态、home、速度/高度/边界及降落判据；A 固化任务完成与最终收尾的组合规则。

必须在测试前填写任务配置中的实际数值。碰撞数据不可获得时标记 unavailable；不能返回 collision_count=0 来暗示没有碰撞。若碰撞或安全返航是硬性成功条件，对应数据缺失应判为无法验收。

## 6. G2：扩展前冻结

### F10：SearchTarget 的感知与真值

- C 定义目标、区域、检测 baseline、目标报告与定位评价；B 提供统一传感器及可用真值获取能力；A 提供独立数据通道和记录。
- 明确“未检测到”和“传感器不可用”的区别。
- 明确目标位置是 Agent 估计还是评测真值，以及真值何时、由谁读取；不把真值隐含在普通 Observation 中。
- 目标报告动作/事件、重复报告、误检、匹配规则、定位误差维度/单位和成功阈值均需样例覆盖。
- 若旧场景无法支持可靠目标真值，先记录限制并保留 ReachPoint 实验；只有 fixtures 的 SearchTarget 不能标为真实搜索能力。

### F11：可复现与比较规则

- 分别固定 Agent seed、任务/场景 seed 和重复次数；列出实际受 seed 控制的因素。
- reset 对车辆、目标、天气、传感器、缓存分别重置什么，初态容差是什么。
- 多个 Agent 使用相同任务与传感器条件；无场景随机化时不能宣称多个独立随机场景。
- 指标冻结名称、单位、计算公式、采样频率影响和缺失值处理；路径长度是采样估计时要明确。
- 失败纳入总样本计数；基础设施错误单列；重试规则预先固定，原始失败记录保留。
- 固定样本数、重复运行门槛、支持的比较结论；小样本报告不外推为普遍性能结论。

