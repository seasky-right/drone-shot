# Plugin Contract v0.2 candidate handoff

Date: 2026-09-25. Contract status: candidate, pending affected-party
confirmation. These are extension tasks, not assignments to named people.
Each Pack must build independently, declare `drone.plugins.v02`, ship a
static manifest, and pass `drone-plugins validate-plugin` with a sample run.
Use only the public `contracts/` and `core/` API in plugin source.
The current builtin Pack registers fourteen v0.1 runtime components through
the v0.2 Registry and ten separate `drone.v02.mock/*` v0.2 components.
The existing `drone.airsim/*` and `drone.reachpoint/*` IDs are legacy runtime
hooks; future v0.2 implementations need explicit IDs, cases, and migration
evidence. Discovery alone is not v0.2 conformance.

| Pack | Proposed component IDs | Capability and context | Acceptance |
| --- | --- | --- | --- |
| AirSim Backend | `drone.airsim/backend` | Control actions, actual camera IDs, frame/time, bounded call policy; no Agent truth | Installed-Pack FakeRpc run and separate real-scene P3/F07/F08 safety evidence |
| ReachPoint and Benchmark | `drone.reachpoint/task`, `drone.reachpoint/evaluator`, `drone.reachpoint/benchmark` | Task/Evaluator truth only; scoring policy version separate from API | Existing v0.1 fixtures and 60-episode Mock comparison reread; F11 before official ranking |
| SearchTarget | `drone.search/task`, `drone.search/evaluator`, Agent IDs under `drone.search/` | Named RGB/depth resource needs, truth hidden from Agent | Success/failure/timeout Mock fixtures, then F10 truth and real-scene checks |
| Scenario/Resource | IDs under `drone.scenario/` | Scenario checksum, seed, resource map, initial states and truth access; Backend load/reset support | Same Urban scenario with Search and Mapping tasks; positive/negative capability cases |
| Coordination | IDs under `drone.coordination/` | Stable vehicle IDs and bindings, explicit sampling/report handlers | Central and per-vehicle two-Mock runs; partial failure, cancellation and missing-vehicle records |

Pass a task owner the exact API string `drone.plugin.api/v0.2`, component
type/ID, JSON Schema config, required actions/sensors/scenario operations,
allowed context, sample/negative fixtures, and wheel entry point. Do not ask
plugin authors to edit `core/` to register a new component. Protocol changes
need a new version and migration rule. Real AirSim, SearchTarget and formal
Benchmark acceptance remain distinct from this Core technical handoff.

For each Pack, include explicit `--component-cases` with actual type-specific
hook inputs and a runtime sample where an Episode combination applies.
`passed` requires hook execution and valid returns, not factory/close alone.
Unselected v0.2 components remain `unchecked`; explicitly marked v0.1
components and protected Backends without explicit enable remain
`unsupported`. Include a failure case for each supplied type.
Backends must report actual action/sensor resources after construction. A
request for hard cancellation fails preflight until interruption support has
been verified in the executor. Runtime Providers must release resources on
success and failure; Result Processors receive only read-only result access.
